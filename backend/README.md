# AI Life Planner — Backend

Backend de los **Módulos 1 a 4** + el primer tramo del **Evidence Engine** (Fase 4 adelantada) + el **Personal Productivity Model** (Fase 3 adelantada) + el primer tramo de **Hábitos avanzados** (Fase 5 adelantada): registro/login, perfil, preferencias, disponibilidad, eventos, tareas, objetivos, hábitos recurrentes, el **Planning Engine** ("Optimizar mi día", replanificación, "¿qué hago ahora?", panel "¿Por qué?" con evidencia científica real y confianza que aprende del historial real de finalización del usuario) y el **asistente conversacional**. Con esto el MVP completo descrito en la sección 21 del brief y la sección B del [blueprint de arquitectura](../blueprint.html) ya funciona de punta a punta.

## Qué incluye

**Módulo 1 — Fundación**
- `POST /v1/auth/register`, `/login`, `/refresh` — autenticación con JWT (access token de 30 min + refresh de 30 días).
- `GET/PATCH/DELETE /v1/users/me` — perfil, incluida la eliminación de cuenta (derecho de borrado desde el MVP, sección J del blueprint).
- `GET/PUT /v1/users/me/preferences` — preferencias de planificación (horarios preferidos, reglas de descanso).
- `GET/POST/DELETE /v1/availability` — disponibilidad semanal recurrente (trabajo/escuela/personal).

**Módulo 2 — Eventos, tareas y objetivos**
- `GET/POST/GET{id}/PATCH/DELETE /v1/events` — eventos fijos del calendario (inamovibles; el Planning Engine nunca los reprograma solo).
- `GET/POST/GET{id}/PATCH/DELETE /v1/tasks` — tareas con prioridad, duración estimada, nivel de concentración, categoría, fecha límite, estado y dependencia opcional de otra tarea propia. `GET /v1/tasks` acepta `?status=` y `?category=`.
- `GET/POST/GET{id}/PATCH/DELETE /v1/goals` — objetivos con horizonte (`hoy` / `semana` / `mes` / `largo_plazo`) y `confirmed_by_user` (siempre `true` en este módulo, porque el usuario los crea directamente — ver `app/models/goal.py`).

**Módulo 3 — Planning Engine**
- `POST /v1/planning/optimize` — "Optimizar mi día" (sección 7 del brief): reconstruye el plan completo de una fecha desde cero, a partir de eventos, disponibilidad recurrente, tareas pendientes y preferencias.
- `GET /v1/planning/day/{date}` — el plan vigente de una fecha (404 si todavía no se generó).
- `POST /v1/planning/replan` — replanificación (sección 8): los bloques de tareas cuyo inicio ya pasó quedan intactos, solo se reoptimiza el resto del día con las tareas que sigan pendientes en ese momento.
- `GET /v1/planning/now` — "¿Qué hago ahora?" (sección 18): si no hay plan para hoy, lo genera solo; si ahora mismo hay un bloque en curso lo dice, si hay un hueco antes del siguiente bloque sugiere una tarea que quepa ahí.
- `GET /v1/planning/streak` — días consecutivos con un plan generado (`current_streak`) y si hoy ya tiene uno (`has_plan_today`), calculado de verdad contando `day_plans.date` hacia atrás desde hoy — no un contador de mentira. Pensado para el encabezado de "Mi día" en el frontend (petición explícita de Daniel de un elemento de enganche diario, ver `frontend/README.md`, sección "Sistema de diseño"). Si hoy todavía no tiene plan, la racha no se corta por eso solo — solo se rompe si falta un día completo.
- `GET /v1/planning/week/{start_date}` — 7 días desde `start_date`, cada uno con `has_plan` y sus bloques reales si ya se optimizó ese día. Nunca genera planes nuevos (a diferencia de `/now`) — cierra el hueco de API que el frontend identificó al construir "Mi semana" (ver `frontend/README.md`).
- `GET /v1/explanations/{block_id}` — panel "¿Por qué?" (sección 12): separa siempre datos del usuario / regla del sistema / evidencia (`null` hasta la Fase 4) / inferencia de IA, con su nivel de confianza. 404 en bloques que son eventos (el usuario los puso él mismo, no hay nada que explicar) o que pertenecen a otro usuario.

El motor en sí (`app/planning/engine.py`) es Python puro, sin FastAPI ni SQLAlchemy — recibe dataclasses, devuelve dataclasses, y se prueba con pytest normal sin DB ni HTTP (`tests/test_planning_engine.py`, 10 pruebas, incluyendo el ejemplo exacto de la sección 29 del blueprint). `app/planning/service.py` es la única pieza que sabe traducir entre la base de datos y el motor.

**Módulo 4 — Asistente conversacional (ahora con IA real)**
- `POST /v1/assistant/message` — sección 16 del brief. Recibe `{"message": "..."}` y devuelve `{action, reply, day_plan, goal}`: siempre actúa sobre datos reales del usuario (nunca un texto genérico de relleno), y cuando corresponde, la respuesta trae el `DayPlan` o el `Goal` que acaba de crear o modificar de verdad.
- **El intérprete de intención ahora es Claude real** (`app/assistant/llm_client.py`, con `ANTHROPIC_API_KEY` configurada — modelo `claude-haiku-4-5-20251001`, tool use forzado contra un solo tool `classify_intent`), no solo los siete ejemplos literales de la sección 16: entiende paráfrasis coloquiales de las mismas seis acciones (`whats_next`/`optimize_day`/`replan_day`/`create_goal`/`clarify`/`unrecognized`) que el motor de reglas nunca hubiera reconocido — por ejemplo *"ando bien muerto, no doy una, ve viendo qué puedo hacer con lo que me queda del día"* clasifica como `replan_day` con la señal de fatiga, igual que *"reorganiza mi día, estoy muy cansado"*. Verificado con un smoke test real contra la API (`tests/test_assistant_llm_parser.py::test_llm_real_clasifica_los_siete_ejemplos_del_brief`, detrás de `RUN_LIVE_LLM_TESTS=1` para no gastar crédito en cada corrida de `pytest`) y con llamadas reales de punta a punta contra `/v1/assistant/message`.
- El LLM **solo clasifica la intención** — nunca redacta la respuesta final ni decide qué hacer con el Planning Engine. `app/assistant/service.py` sigue construyendo la respuesta a partir de datos reales del plan/objetivo, exactamente como antes (sección 28 del blueprint: "el LLM interpreta, nunca decide la agenda") — el cambio quedó aislado a `parser.py`/`llm_client.py`, tal como estaba planeado desde que el intérprete era solo reglas.
- **Con resiliencia real, no solo en el happy path**: sin `ANTHROPIC_API_KEY`, o si la llamada a la API falla por cualquier motivo (red, rate limit, respuesta sin tool use), `parser.parse()` cae automáticamente al motor de reglas original (`parser.parse_rule_based`, los mismos siete ejemplos de antes) — el asistente nunca se cae por completo solo porque el LLM tuvo un hiccup. Frases donde adivinar sería arriesgado — como *"tengo que terminar este proyecto mañana"*, donde no está claro a cuál tarea se refiere — siguen devolviendo una pregunta aclaratoria en vez de modificar algo sin permiso (principio 4 del brief: "la IA recomienda, no impone"), sea cual sea el intérprete activo. Un mensaje no reconocido dice honestamente que no lo entiende y lista ejemplos, en vez de responder con relleno genérico.

**Evidence Engine (Fase 4, adelantada) — evidencia científica real en el panel "¿Por qué?"**
- `GET /v1/explanations/{block_id}` ahora puede devolver, en el campo `evidence`, una cita real y verificable en vez de siempre `null`: fuente, autores, año, tipo de estudio, DOI, nivel de evidencia (sólida/moderada/limitada) y las **limitaciones** de ese estudio — nunca solo la conclusión favorable.
- El catálogo (`evidence_sources`, `app/models/evidence.py`) es **estático y curado a mano** — no hay endpoint para crearlo ni editarlo, y el LLM (cuando exista) solo podrá citar entradas que ya estén aquí, nunca inventar una. Las seis entradas de hoy (`app/planning/evidence_catalog.py`) se investigaron y cada DOI se verificó contra [Crossref](https://www.crossref.org/)/PubMed antes de escribirse. Las primeras tres respaldan la colocación de un bloque en una ventana preferida:
  - **Concentración** → Rubinstein, Meyer & Evans (2001), *Journal of Experimental Psychology: Human Perception and Performance* — costo de cambiar de tarea. Evidencia moderada (estudio de laboratorio).
  - **Estudio** → Cepeda, Pashler, Vul, Wixted & Rohrer (2006), *Psychological Bulletin* — efecto de espaciamiento en el recuerdo. Evidencia sólida (meta-análisis).
  - **Entrenamiento** → Chang, Labban, Gapin & Etnier (2012), *Brain Research* — ejercicio agudo y rendimiento cognitivo. Evidencia sólida (meta-análisis).
- Solo se adjunta evidencia cuando el bloque **de verdad** cayó en la ventana de preferencia correspondiente (`matched_preference_label` en `app/planning/engine.py`, un campo estructurado, no texto parseado) — un bloque colocado por "primer hueco disponible" nunca trae una cita, porque ahí no hay ninguna conexión científica real que citar.
- En una replanificación, un bloque bloqueado (ya pasó o está en curso) **conserva** la evidencia que ya tenía en vez de tener que resolverla de nuevo — ver `app/planning/service.py::generate_replan` y las pruebas en `tests/test_planning_evidence_service.py`.
- **`GET /v1/explanations/general` (ampliación del catálogo)** — las otras tres entradas respaldan reglas GENERALES del motor, no la colocación de un bloque en particular, así que viven en su propio endpoint en vez de forzarse dentro del panel "¿Por qué?" de un bloque (el esquema solo modela una evidencia *por bloque*, y estas citas no respaldan ningún bloque específico):
  - **Descanso entre bloques** → Ariga & Lleras (2011), *Cognition* — pausas breves y atención sostenida. Evidencia moderada (estudio de laboratorio).
  - **Nunca comprimir el sueño** → Lim & Dinges (2010), *Psychological Bulletin* — impacto cognitivo de la privación de sueño de corto plazo. Evidencia sólida (meta-análisis, 70 estudios).
  - **Combinar prioridad y cercanía de fecha límite (no ordenar solo por urgencia)** → Zhu, Yang & Hsee (2018), *Journal of Consumer Research* — el "mere urgency effect" (la gente tiende a preferir lo urgente sobre lo importante aunque salga peor). Evidencia moderada (cinco experimentos de comportamiento).
  - Esta era la ampliación pendiente que ya estaba documentada aquí como "investigada pero sin lugar donde mostrarla" — el lugar que faltaba (`app/planning/evidence.py::list_general_evidence` + este endpoint) ya existe, así que las tres citas se agregaron al catálogo (migración `20d13a6ee95c`).

**Personal Productivity Model (Fase 3, adelantada) — confianza que aprende del historial real, no simulada**
- La única señal real que existe hoy sobre "¿esto le funciona al usuario?" es si una tarea colocada antes en una ventana preferida terminó **completada** (`tasks.status`). No hay ningún timestamp de duración real registrado en ningún lado todavía, así que este módulo **no** ajusta estimaciones de duración — solo la confianza en la ventana elegida. Inventar una señal de duración que no se mide sería justo lo que la sección 11 del brief prohíbe.
- `recommendation_explanations.matched_preference_label` (migración `16e005952f99`) persiste, desde ahora, la etiqueta ("concentración" / "estudio" / "entrenamiento") de la ventana preferida en la que de verdad cayó cada bloque — antes se calculaba y se descartaba justo después de resolver la evidencia científica. Los planes generados antes de esta migración quedan en `NULL` a propósito: el historial arranca desde que existe la columna, nunca se estima retroactivamente.
- `app/planning/service.py::compute_personal_stats` cuenta, por etiqueta y por usuario, cuántos bloques de días **anteriores** al que se está planificando terminaron en una tarea completada. Con eso, `app/planning/engine.py::_personal_model_inference` (función pura, sin DB, como el resto del motor) decide el texto de "Inferencia de IA" y el nivel de confianza de cada bloque nuevo:
  - Menos de `PPM_MIN_SAMPLE` (5) bloques históricos con esa etiqueta → confianza `baja`, con el conteo real ("3/5 bloques registrados") en vez de un genérico "no tengo datos".
  - 5 o más bloques y ≥70% completados → confianza `alta`, citando la cifra real ("completaste 5 de 5, 100%").
  - 5 o más bloques y entre 40% y 70% completados → confianza `media`, con el mismo tipo de cifra.
  - 5 o más bloques y menos del 40% completados → confianza `baja`, pero con una explicación honesta de que esa ventana puede no estar funcionando, sugiriendo revisar las preferencias — nunca oculta un mal resultado.
- Un bloque colocado por "primer hueco disponible" (sin ventana preferida asociada) sigue sin ningún análisis de historial personal — no hay ninguna etiqueta que cruzar, así que decirlo de otra forma sería inventar una conexión.
- No hay endpoint propio para consultar estas estadísticas directamente todavía — se ven donde ya se veían `ai_inference`/`confidence`, en `GET /v1/explanations/{block_id}` y el panel "¿Por qué?" del frontend, sin que ese panel haya necesitado ningún cambio.

**Hábitos avanzados (Fase 5, adelantada) — metas recurrentes, con confirmación explícita siempre**
- `GET/POST /v1/habits`, `GET/PATCH/DELETE /v1/habits/{id}` — CRUD normal de hábitos: título, veces por semana objetivo, duración por sesión, nivel de concentración, categoría opcional y, opcionalmente, el `goal_id` de un objetivo existente del mismo usuario al que pertenece.
- `GET /v1/habits/{id}/week` — progreso REAL de la semana actual (lunes de "hoy" en la hora de pared del usuario) + sesiones propuestas para completar lo que falte. Nada de esto se inventa: `confirmed_this_week`/`completed_this_week` se calculan contando tareas reales con `habit_id` apuntando a este hábito y `deadline` dentro de esa semana (`app/habits/service.py::week_progress`) — un hábito nunca coloca nada en el calendario por sí mismo, reutiliza `tasks.deadline` en vez de inventar una tabla nueva de "ocurrencias".
- `POST /v1/habits/{id}/confirm-week` — el ÚNICO lugar donde una sesión propuesta se vuelve una tarea real, y solo con la lista exacta de sesiones que el cliente manda de vuelta (nunca más de las que de verdad faltan — se valida contra `remaining_to_suggest`, 422 si no). Mismo principio que ya regía `Goal.confirmed_by_user` (punto 14 del brief: "NO debe crear objetivos arbitrarios sin confirmación del usuario"), extendido aquí a las sesiones que un hábito genera — ver el docstring de `app/models/habit.py`.
- Las tareas confirmadas son tareas reales de cualquier otro lado de la app: aparecen en `GET /v1/tasks`, las coloca "Optimizar mi día" como cualquier otra, y al completarlas actualizan `completed_this_week` — sin necesitar ningún cambio en el Planning Engine (`app/planning/engine.py` sigue sin saber que los hábitos existen).
- Límite conocido y documentado a propósito: `GET .../week` solo opera sobre la semana ACTUAL — todavía no hay forma de consultar el progreso de una semana pasada o futura de un hábito. Mismo tipo de recorte que "Disponibilidad" (solo permite crear, no editar): se documenta aquí en vez de disimularlo, se amplía si hace falta más adelante.

### El intérprete de intención: Claude real, con motor de reglas como respaldo

El blueprint (sección F) especifica un LLM para esta capa. Ahora que existe una `ANTHROPIC_API_KEY` real del proyecto (guardada en `.env`, nunca en el repo — ver `.gitignore`), `app/assistant/parser.py::parse()` llama primero a `app/assistant/llm_client.py::classify_intent`, con tool use forzado contra el mismo contrato `Intent` (`app/assistant/intents.py`) que ya consumían el router y el service — el cambio quedó exactamente tan aislado como se había planeado: no tocó el router, el service, ni el Planning Engine.

El motor de reglas original (`parser.parse_rule_based`) no se borró — sigue siendo el respaldo determinista: si no hay key configurada, o la llamada a la API falla por cualquier motivo, `parse()` cae ahí en vez de propagar el error (ver `app/assistant/llm_client.py::LLMUnavailable`). Esto no es solo tolerancia a fallas — es honestidad con la sección 11 del brief ("no inventar, no afirmar lo que no se verificó"): si el LLM no puede clasificar, el sistema nunca inventa una clasificación a partir de una excepción, usa el camino determinista que sí se puede probar de punta a punta sin depender de un proveedor externo.

La disciplina de "no dar por probado lo que no se corrió de verdad" (secciones 11 y 34 del brief) sigue aplicando, ahora en la otra dirección: la suite normal de `pytest` (`tests/test_assistant_parser.py`, `tests/test_assistant_api.py`) sigue corriendo 100% determinista, sin red ni costo — un fixture autouse en `tests/conftest.py` desactiva el LLM real para toda la suite por defecto, así que correr `pytest` nunca gasta crédito de la API de Anthropic ni depende de que esté disponible. El intérprete con Claude real se prueba aparte en `tests/test_assistant_llm_parser.py`: la mayoría con el cliente de Anthropic mockeado (determinista, cubre el armado del `Intent`, el fallback en cada tipo de falla), más un smoke test contra la API de verdad (los siete ejemplos del brief) que corre a mano con `RUN_LIVE_LLM_TESTS=1` — la verificación real que pide la disciplina del proyecto, sin dejarla corriendo (ni gastando crédito) en cada `pytest`.

Todo está aislado por usuario: cada query filtra por el `user_id` del token, y un usuario nunca puede leer, editar ni borrar un recurso ajeno, ni ver la explicación de un bloque ajeno (verificado en `tests/test_*` para cada módulo).

## Qué NO incluye todavía

El Evidence Engine hoy cubre seis temas con una cita cada uno (concentración/estudio/entrenamiento por bloque + descanso/sueño/priorización como reglas generales) — es un catálogo real pero deliberadamente chico, no una biblioteca completa; crece agregando filas investigadas a mano a `app/planning/evidence_catalog.py`, nunca generándolas. Las explicaciones siguen siendo redactadas por plantillas en Python (reglas + datos del usuario +, cuando aplica, una cita del catálogo y ahora también el historial real de finalización), no por un LLM — eso ya cumple el "nivel 1" de explicabilidad que pedía el MVP (sección 21) sin necesitar todavía una API key de un modelo de lenguaje. El Personal Productivity Model (ver sección de arriba) solo aprende de finalización por ventana preferida — no ajusta duraciones estimadas, porque no existe ningún dato real de duración registrada para hacerlo sin inventar. Los hábitos (ver sección de arriba) todavía no se vinculan solos a un objetivo — `goal_id` existe en el esquema, pero nada del backend crea un hábito automáticamente a partir de un objetivo todavía; y `GET /v1/habits/{id}/week` solo cubre la semana actual, sin historial de semanas pasadas.

## Cómo correrlo

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # y edita JWT_SECRET_KEY antes de producción
alembic upgrade head   # crea/actualiza el esquema de la base de datos
uvicorn app.main:app --reload
```

La API queda en `http://localhost:8000`, con documentación interactiva en `http://localhost:8000/docs`.

## Cómo correr las pruebas

```bash
source .venv/bin/activate
pytest -v
```

Cada prueba usa una base SQLite aislada en un directorio temporal (ver `tests/conftest.py`), así que no tocan tu base de desarrollo.

## Decisiones técnicas (y por qué)

- **SQLite en desarrollo/test, PostgreSQL en producción**: el modelo de datos (UUIDs como string, tipos estándar) es compatible con ambos sin cambios de código — solo cambia `DATABASE_URL` (y el `alembic upgrade head` se corre contra Postgres igual que contra SQLite).
- **Migraciones con Alembic desde el Módulo 2**: `alembic/env.py` toma la URL de `app.config.get_settings()` (no de un valor estático en `alembic.ini`), así que `DATABASE_URL` gobierna tanto la app como las migraciones desde un solo lugar. La app ya **no** crea tablas automáticamente al arrancar — `alembic upgrade head` es un paso explícito, deliberado antes de tener datos reales que proteger.
- **`depends_on_id` en tareas**: dependencia simple de una tarea a otra del mismo usuario, validada en el router (existe, pertenece al usuario, no es auto-referencia). El Planning Engine (Módulo 3) la usará para no programar una tarea antes de que su dependencia esté completada; no hay todavía detección de dependencias circulares de más de un nivel — se añade si el Módulo 3 lo necesita.
- **Refresh tokens sin estado en servidor**: por simplicidad del MVP, el refresh token es un JWT firmado, no un registro en base de datos. Esto significa que **no se puede revocar un refresh token individual** antes de que expire (ej. si un dispositivo se pierde). Es una limitación conocida y aceptable para el MVP, documentada aquí para no perderla de vista — la sección J del blueprint prevé rotación completa de tokens como endurecimiento posterior.
- **Passlib + bcrypt** para hashing de contraseñas, alineado con la sección J del blueprint. Nota de compatibilidad: se fija `bcrypt==4.0.1` en `requirements.txt` porque versiones más nuevas de `bcrypt` rompen la detección de versión de `passlib` 1.7.4.
- **Heurística de asignación por prioridad, no un solver combinatorio** (sección G del blueprint): se ordenan las tareas por una puntuación de urgencia (prioridad + cercanía de fecha límite) y se colocan una por una en el mejor hueco disponible. Es más simple de explicar bloque por bloque que un solver tipo OR-Tools, y suficiente para la carga de un solo día — el upgrade a un solver queda para cuando los datos reales demuestren que hace falta, no antes.
- **`availability_blocks` se tratan siempre como tiempo ocupado**, sin importar su `type` (trabajo/escuela/personal/otro): todos representan un compromiso recurrente que le resta tiempo disponible al usuario para tareas. El `type` es solo metadato para mostrarlo con claridad, no cambia el comportamiento del motor.
- **Los objetivos (`goals`) todavía no se planifican solos**: convertir un objetivo en una tarea programable hoy es, por ahora, una acción manual del usuario (crear la tarea él mismo, o crear un hábito aparte y enlazarlo con `goal_id`). Descomponer un objetivo automáticamente en un hábito (en vez de que el usuario lo cree él mismo) sigue pendiente — ver la sección de Hábitos avanzados arriba.
- **Un hábito reutiliza `tasks.deadline` en vez de una tabla de "ocurrencias" nueva**: cada sesión CONFIRMADA de un hábito es una fila real de `tasks` con `habit_id` puesto y `deadline` al final del día sugerido — así el Planning Engine, "Mi día"/"Mi semana" y el CRUD de tareas la tratan exactamente igual que cualquier otra tarea, sin necesitar ningún cambio en `app/planning/engine.py`. El costo de esta simplicidad: una sesión de hábito no puede tener una hora exacta dentro del día, solo una fecha límite — aceptable porque el usuario nunca eligió una hora, solo un día.
- **Confirmar sesiones de un hábito es SIEMPRE una acción explícita, nunca automática**: `POST /v1/habits/{id}/confirm-week` valida que el cliente no mande más sesiones de las que de verdad faltan (`remaining_to_suggest`) y rechaza con 422 si lo hace — mismo principio que ya regía `Goal.confirmed_by_user` (punto 14 del brief), extendido aquí.
- **El catálogo de evidencia es estático y sin API propia, a propósito**: exponer un `POST /v1/evidence` (o dejar que el asistente "agregue una fuente" a partir de una conversación) sería la forma más rápida de terminar con citas inventadas en el panel "¿Por qué?" — el único camino para que una fuente entre al catálogo es que alguien la busque, la verifique contra Crossref o el DOI directo, y la agregue a mano a `app/planning/evidence_catalog.py`. Es más lento a propósito.
- **Una sola evidencia por bloque, nunca varias**: el esquema (sección E del blueprint) modela `evidence_ref_id` como una referencia única — si un bloque calificara para más de una cita, se prioriza la de evidencia más sólida (`app/planning/evidence.py::find_evidence_for_label`) en vez de mostrar varias a medias.
- **`now` se calcula en la zona horaria del usuario** (`app/planning/service.py::local_now`), no en UTC del servidor — los horarios del plan son "hora de pared" (se arman combinando una fecha con las horas de `wake_time`/`sleep_time`, sin tzinfo), así que compararlos contra un `datetime.utcnow()` habría producido resultados incorrectos para casi cualquier usuario fuera de UTC.
- **El Personal Productivity Model calcula sus estadísticas en `service.py`, nunca dentro de `engine.py`**: el motor sigue siendo Python puro sin DB (mismo principio que el Evidence Engine, ver arriba). `compute_personal_stats` consulta la base de datos y arma un `dict[str, LabelStats]` simple; `engine.py::_personal_model_inference` solo recibe ese diccionario ya armado y decide el texto/confianza — es una función pura, tan testeable como el resto del motor.
- **"Completada" es el estado ACTUAL de la tarea, no una confirmación del día exacto en que se hizo**: las tareas no están ancladas a un día (siguen "pendientes" hasta que se marcan a mano — el mismo hallazgo documentado en `tests/test_planning_week.py`), así que no existe un timestamp de "se completó este bloque, este día" en ningún lado. Es una limitación conocida y aceptada, documentada aquí a propósito en vez de disimularla — es la señal más honesta que se puede calcular con el esquema actual, sin inventar una columna de fecha de finalización que hoy no existe.

- **El intérprete de intención del asistente ahora es Claude real, con el motor de reglas como respaldo** (Módulo 4): ver la sección "El intérprete de intención: Claude real, con motor de reglas como respaldo" arriba. `Intent` (`app/assistant/intents.py`) sigue siendo el contrato compartido que mantuvo ese cambio aislado a `parser.py`/`llm_client.py`.
- **El asistente nunca adivina sobre datos existentes**: crear un objetivo nuevo a partir de "quiero entrenar..." es seguro porque el usuario lo está pidiendo explícitamente en ese mismo mensaje; pero modificar una tarea ya existente a partir de una frase ambigua ("tengo que terminar el proyecto mañana", sin decir cuál) no lo es — ahí el asistente pregunta en vez de adivinar a cuál tarea se refiere.

## Siguiente módulo

Con el MVP funcional de punta a punta, el primer tramo del Evidence Engine ya conectado al panel "¿Por qué?", el primer tramo del Personal Productivity Model (Fase 3, aprendiendo de verdad de la finalización real del usuario por ventana preferida), el primer tramo de Hábitos avanzados (Fase 5, metas recurrentes con progreso real y confirmación explícita) y ahora el asistente conversacional con Claude real (Módulo 4), lo que queda en el roadmap (sección L del blueprint) son: seguir ampliando el catálogo de evidencia con más temas (por ejemplo, procrastinación o manejo de interrupciones) e investigar cada cita con la misma disciplina que las actuales; ampliar el Personal Productivity Model a más señales conforme el esquema las vaya soportando (por ejemplo, duración real si algún día se registra); ampliar Hábitos avanzados (historial de semanas pasadas, descomposición automática de un objetivo en un hábito propuesto); y Suscripción/pago (Stripe, sección K del blueprint — el bloque "Plan actual: Free" de Ajustes ya está ahí a propósito, esperando ese flujo, pendiente de una API key de Stripe).
